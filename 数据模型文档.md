# 匿名书信治愈社区 · 数据模型文档

> 适用范围：「标准 MVP」路线。本文档是**可直接落地的数据库设计**，配套《架构设计文档》《技术选型文档》。
> 技术约定：PostgreSQL 15+ / Prisma 5.x。主键统一 `BigInt`（雪花/自增），所有时间 `timestamptz`（UTC 存储）。
> 阅读顺序：先看 §1 概览与 ER 图，再看 §2 枚举字典，§3 各表详解，§4 完整 Prisma schema，§5 索引与约束，§6 软删除/审计/数据权利约定。

```
       │claim_id  │      └─────────────────┘              │
       └────┬─────┘                                       │
            │ 1:1 claim_id → reply                         │
            │                                              │
   ┌────────▼─────────┐   ┌─────────────────┐   ┌──────────▼─────────┐
   │ moderation_records│   │  sensitive_hits │   │   audit_logs       │
   │ (target letter/   │   │ (target letter/ │   │ (admin operations) │
   │  reply)           │   │  reply)         │   └────────────────────┘
   └───────────────────┘   └─────────────────┘

   conversations(user_a, user_b, source_letter_id) —— P1，复用 letters/replies

```

核心链路：`users` 写 `letters` → 另一 `users` 产生 `letter_claims`（抢占）→ 写 `replies` → 原作者产生 `reply_feedbacks`。治理三张表（reports / moderation_records / sensitive_hits）旁挂在 letters/replies 上。

## 三、各表详解（关键字段语义）

### 3.1 users
- `nickname`：对外匿名昵称，可改；与 `user_id` 解耦。
- `email` / `phone`：二选一，**唯一**，建议应用层加密或脱敏存储；用于防重复注册与通知。
- `trust_score`：信任分，默认 100，驱动领取额度与等级；由审核/反馈/违规调整。
- `level`：由 `trust_score`、有效回信数、违规记录派生（可定时计算缓存）。
- `interested_topics` / `blocked_topics`：jsonb 数组，分配信件时用。
- `status`：限制/封禁状态；`DELETED` 配合数据删除流程。
- `daily_write_quota` / `daily_claim_quota`：每日限额，新用户默认 1 / 1~2，信誉提升可调高。

### 3.2 letters
- `title` 可空（计划书：标题选填）。
- `content`：纯文本/有限格式（分段/加粗/引用/分隔线）。
- `reply_preference`：jsonb，含 `wantedReplyTypes`、`allowMultiple`、`closeAfterFirstReply`。
- `max_replies`：默认 1，范围 1~3。
- `published_at`：审核通过进入 `WAITING_CLAIM` 时写入；`created_at` 为提交时间。
- `risk_level`：自动检测结果，`HIGH` 强制送审。

### 3.3 letter_claims（抢占核心）
- 唯一约束 `(letter_id, reader_id)`：同一人不重复领取同一信。
- `expires_at = claimed_at + 24h/48h`；到期未回信由 Worker 置 `EXPIRED` 并释放信件回 `WAITING_CLAIM`。
- 活跃 `CLAIMED` 数受 `letters.max_replies` 限制（应用层 + 部分唯一索引保障）。

### 3.4 replies
- `claim_id` 关联领取，保证「先领取再回信」。
- `feedback` 已移到独立表 `reply_feedbacks`（便于扩展，且语义是收信人对回信的评价）。
- `PUBLISHED` 后触发 `REPLY_RECEIVED` 通知。

### 3.5 reply_feedbacks
- `(reply_id, rater_id)` 唯一；反馈**不公开**，仅用于回信质量评分与 `trust_score`。

### 3.6 moderation_records / sensitive_hits
- `moderation_records`：每次审核动作一条，`operator_id` 为 null 表示系统自动；全程留痕。
- `sensitive_hits`：自动检测命中的明细（类型、匹配片段位置、是否已遮挡），供后台展示与遮挡。

### 3.7 audit_logs
- 记录所有管理员写操作：`operator_id`、`action`、`target_type`、`target_id`、`before/after`(jsonb)、`ip`、`created_at`。

## 五、索引、约束与并发要点

### 5.1 关键约束
| 表 | 约束 | 目的 |
|---|---|---|
| users | `email`/`phone` 唯一 | 防重复注册 |
| user_blocks | `(blockerId, blockedId)` 唯一 | 防重复拉黑 |
| letter_claims | `(letterId, readerId)` 唯一 | 同人不重复领取 |
| replies | `claimId` 唯一 | 一次领取一封回信 |
| reply_feedbacks | `(replyId, raterId)` 唯一 | 一人一评 |
| daily_stats | `statDate` 唯一 | 每日一行 |

### 5.2 关键索引
- `letters(status, category)`：待回信箱按主题+状态分配的主查询路径。
- `letter_claims(status, expiresAt)`：Worker 扫描超时领取。
- `reports(status, priority)`：审核后台队列排序。
- `notifications(userId, isRead)`：未读通知拉取。

### 5.3 领取抢占（核心并发逻辑，伪 SQL）
```sql
-- 在一个事务里完成「挑一封可领取的信并锁定」
BEGIN;
SELECT l.id
FROM letters l
WHERE l.status = 'WAITING_CLAIM'
  AND l.category = ANY($interestedTopics)      -- 主题偏好（可放宽）
  AND l.risk_level <> 'HIGH'                    -- 高风险不进普通池
  AND l.author_id <> $readerId                  -- 不读自己的信
  AND NOT EXISTS (                              -- 没被该读者领过/跳过
    SELECT 1 FROM letter_claims c
    WHERE c.letter_id = l.id AND c.reader_id = $readerId
  )
  AND (
    SELECT count(*) FROM letter_claims c2
    WHERE c2.letter_id = l.id AND c2.status IN ('CLAIMED','REPLIED')
  ) < l.max_replies
ORDER BY l.published_at ASC
FOR UPDATE OF l SKIP LOCKED        -- 跳过已被并发锁定的信
LIMIT 1;

-- 若取到 letterId：
INSERT INTO letter_claims(letter_id, reader_id, status, claimed_at, expires_at)
VALUES ($letterId, $readerId, 'CLAIMED', now(), now() + interval '24 hours');

UPDATE letters SET status = 'CLAIMED' WHERE id = $letterId;  -- 单回信场景
COMMIT;
```
- 多回信（`max_replies > 1`）场景：信件可保持 `WAITING_CLAIM` 直至达上限，状态推进由应用层判断。
- Redis 额外加 `SETNX claim:lock:{letterId}` 短锁兜底，防极端并发。
- 跳过的信用 Redis `SADD skip:{readerId} {letterId}` 记录，短期内不再分配。

## 六、软删除、审计与数据权利

| 主题 | 约定 |
|---|---|
| **软删除** | `users.deletedAt`、`letters.closedAt` 等用时间戳标记；用户注销 → `status=DELETED` + 匿名化（清昵称/凭据），保留必要风控记录至合规期满 |
| **数据导出** | 提供导出接口：用户本人的信件、回信、收藏，异步生成文件存对象存储，限时下载 |
| **数据删除申请** | 走人工/流程审核，区分「立即匿名化」与「合规保留」字段 |
| **审计留痕** | 所有管理员写操作进 `audit_logs`；所有审核动作进 `moderation_records`，不可物理删除 |
| **敏感字段存储** | `email`/`phone` 应用层加密或哈希索引；正文中检测到的联系方式按 `sensitive_hits` 标记并可遮挡 |
| **时间脱敏** | 对外展示用模糊时间（「两天前」），精确 `created_at` 仅内部/审核可见（计划书：隐藏精确时间防身份推测） |
